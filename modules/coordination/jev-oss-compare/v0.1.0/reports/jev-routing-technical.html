How the gates decide, and what we have measured so far

One flow, three lanes, one small pilot. The numbers below are discovery-only: they say the pipeline runs end to end, not that it is right. Accuracy and catch-rate are not measured yet.

Gate → decision → recovery

Each gate packs the relevant pins (your recorded constraints) and a short brief, asks a decision model for one typed route, and hands the agent that route before the tool call proceeds. A miss costs a re-ask or a plan revision, not a wasted session.

Plain-text version of the same flow:

  1. Agent wants to call a tool.
  2. Gate packs pins and brief.
  3. Jev decision gate returns one route.
  4. Clear → proceed.
  5. Missed constraint → reconfirm_intent.
  6. Plan drift → rethink_plan.
  7. Unverified claim → research_more or dispatch_verifier.
  8. Unsafe or unsure → escalate to human.

Why cheap gates? A full model pass per decision is slow and expensive enough that people skip checks. A small specialist answer (one route token) is cheap enough to run at every gate, so the misses get caught at step three instead of step eighty.

Read the numbers this way

  • Accuracy and catch-rate: not measured. The pilot checked plumbing — jobs scheduled, scored, routed — against one non-blind session stream.
  • Checkpoint confidence is uncalibrated. The model card reports ECE 0.213 and a median confidence near 0.009 on its own synthetic tasks; the specialist was trained on four synthetic workflows, not coding traces. Treat probability values as model-defined, not correctness.
  • Median 4752.66 ms is a CPU pilot figure on batched local inference, not a production latency claim for any lane.
  • Hosted latency and pricing are third-party claims (TypeSafe Jev 1.13 served through OpenRouter); they were observed live in our harness, not guaranteed by us.

The receipts behind the pilot rows live in reports/ in this repository (for example runs/laya-pilot-20260929.json). The full comparison dashboard is the sibling page jev-oss-compare.html.
